## Why this batch

The C1 commit contract (`git-commit-implementation-contract-2026-10-07.md` §C02–C04) records that the
original commit dialog has an **Include unstaged changes** checkbox
(`git-action-include-unstaged-changes`, sent as `includeUnstaged`) and that the worker runs a stage
helper (`add -A` fallback) before `commit -m`. C1 deliberately narrowed to "commit the existing index
only", so the checkbox had no consumer. This batch adds the stage step behind a real checkbox.

## Ordering and safety

1. The accepted snapshot is re-verified against the current index (`sameCommitSelection`) **before** the
   stage step, so a competing stage is not overwritten (proved by the stale-index test: the request is
   rejected and the index bytes are unchanged).
2. The stage step runs before dispatch. A failure there is `Rejected`, never `UnknownOutcome`; the
   controller re-reads the real index, so the UI shows the true staged state.
3. If staging leaves the index empty the request is rejected without invoking `git commit`.
4. The fixed argv policy is unchanged (`core.hooksPath=/dev/null`, `commit.gpgSign=false`,
   `--no-verify`, `--no-gpg-sign`, no amend, no empty commit).
5. For a request without the flag, `stagedByRequest` must stay `false` and `stagedIndexDigest` must
   equal the accepted snapshot digest, so the C1 guarantee is unchanged.

## Deviation

The original checkbox defaults to **checked**; this batch defaults to **unchecked** so the existing
explicit-index-only policy stays truthful until the user opts in. That is a product decision, not
original evidence.
